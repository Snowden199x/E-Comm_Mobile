## Buyer: Continue with Google leads straight into registration with the address already verified

**Continue with Google** in the Buyer app now ends in the Buyer registration form whenever the picked Google account has no Buyer account. The person never types the address: the API verifies the ID token, reads the email and name claims from it, and the form opens with those values.

1. `_continueWithGoogle()` gets the ID token from `google_sign_in` and posts it to `POST /api/v1/buyer/google`.
2. The API finds no Buyer for that address and answers `202` with `registration_required: true`, a 64-character `registration_token`, and the token's `email`, `given_name` and `family_name`. The proof lives in the cache for 30 minutes (`BuyerEmailOtpController::PROOF_TTL_MINUTES`), bound to that email.
3. `_openGoogleRegistration()` pushes `RegisterScreen` with the token, the email and the names.
4. Step 1 of the form shows the email filled in, read-only, with a lock icon and a green **Verified with Google** badge in place of the *Verify* link, so the emailed six-digit code is never requested. First and last name are prefilled and stay editable.
5. Submitting posts `google_registration_token` instead of `verification_token`. `BuyerRegistrationController` looks up the cached proof, requires it to match the submitted address, marks the new account's `email_verified_at`, and drops the proof. The new account is still `pending` until an Admin approves it, and the ID photos, birthdate, address and password are still required.

This is Buyer-only. The Rider and Driver apps keep the behaviour documented in their own feature docs.

### Changed

- `lib/features/auth/screens/register_screen.dart` — the email field gets a lock icon while Google verification stands, so "filled in and cannot be edited" is visible rather than only true.
- `docs/features/buyer-app.md` — the Google paragraph described the old "told to register" answer; it now describes the prefilled, locked, verified form.
- Web side (same flow): `docs/features/shared/google-auth/spec.md` gained a Buyer mobile paragraph, and the 15 November log's `BuyerGoogleAuthController` bullet now mentions the `202` proof.

### Verified

- `flutter analyze` on `login_screen.dart`, `register_screen.dart` and `buyer_api.dart`: no errors or warnings. The 19 `info` lints it reports (missing braces on one-line `if`/`for`, deprecated `package:flutter/material.dart`, null-aware element hints) are all in code this change does not touch.

### Gaps

## Rider Google sign-in fails on the phone while the Buyer app works: the package is not registered in the web client's project

On the phone the Rider app answers **Continue with Google** with *Google sign-in closed without an account. If you did not cancel it, this build is not registered in Google Cloud: add an Android OAuth client for vendoph.rider with the SHA-1 of this build.* The Buyer app on the same phone signs in. Everything that the two apps could differ on was measured rather than guessed:

- The installed Rider APK (pulled from the device, `adb pull` of `/data/app/.../vendoph.rider-.../base.apk`, installed 01:38) and the working Buyer build are signed by the same certificate: `apksigner verify --print-certs` reports SHA-1 `dc3bdfda36472f8c4d2a466fbbf1ffe4f5628ec9` for both, `CN=Vendo Debug, OU=Mobile, O=Vendo, L=Manila, ST=Metro Manila, C=PH`.
- Both APKs carry the same server client ID string in `assets/flutter_assets/kernel_blob.bin`: `468116080938-db4garqg6u4nt2q9535s58k77h9t1pc1.apps.googleusercontent.com`.
- Both apps pin `google_sign_in: ^7.2.0`, and their `_continueWithGoogle()` calls `GoogleSignIn.instance.initialize(serverClientId: GoogleAuthConfig.webClientId, clientId: ...)` with the same iOS/macOS client values (empty on Android), then `authenticate()`.
- `vendo_rider/android/app/build.gradle.kts` builds `applicationId = "vendoph.rider"` and signs debug and release with `vendoDebug` (no `key.properties` on this machine), so `./gradlew signingReport` shows SHA-1 `DC:3B:DF:DA:36:47:2F:8C:4D:2A:46:6F:BB:F1:FF:E4:F5:62:8E:C9` for both variants.
- Neither `google-services.json` supplies an OAuth client: both files are Firebase project `vendorider` (`515568012007`) for package `vendoph.rider` with `oauth_client: []`, so they contribute push only.

That leaves one difference the code cannot fix: project `468116080938` has no Android OAuth client for package `vendoph.rider` with SHA-1 `DC:3B:DF:DA:36:47:2F:8C:4D:2A:46:6F:BB:F1:FF:E4:F5:62:8E:C9`. Google refuses the credential before the app sees a token, and `google_sign_in` 7.x surfaces that refusal as `canceled`, which is why the message hedges between a real cancel and a registration problem.

**Server side, measured:** `php artisan config:show services.google` lists `web_client_id` `468116080938-db4garqg6u4nt2q9535s58k77h9t1pc1` and exactly one Android client, `468116080938-ajc6emr9v596ot65fd69si0sp7ac6arv` — the Buyer's. That is the second half of the fix: once the Rider's Android client exists, its client ID must be appended to `GOOGLE_ANDROID_CLIENT_ID` (comma-separated) so it reaches `allowed_client_ids`, because the verifier checks the token's `azp` (the package's own Android client) as well as its `aud` (the web client). Without that the Console fix would move the failure from the phone to a 422 at the API.

**Owner action (Console only, no rebuild):** in Google Cloud project `468116080938` — the project that owns web client `468116080938-db4garqg6u4nt2q9535s58k77h9t1pc1` — APIs & Services → Credentials → Create credentials → OAuth client ID → Android, application type Android, package name `vendoph.rider`, SHA-1 `DC:3B:DF:DA:36:47:2F:8C:4D:2A:46:6F:BB:F1:FF:E4:F5:62:8E:C9`. If a `vendoph.rider` client already exists there with the older machine fingerprint `4F:80:D0:D4:D6:60:49:70:EF:CE:C0:D2:21:70:71:36:15:35:C1:84`, add the new SHA-1 to that client instead. A release build signed with the upload key (`C9:86:6E:DA:E3:7E:3B:7C:ED:AE:19:2B:AC:A1:77:46:DE:32:4F:5A`) needs that fingerprint registered as well. The **Rate this product** dialog on a completed order overflowed by 8px past the right edge of the fifth star on a 360dp-wide phone. Five default `IconButton`s ask for 48dp each (240dp), while an `AlertDialog` leaves 232dp of content width on that screen after its 40dp inset and 24dp content padding — the 8px is exactly that difference.

- `lib/features/orders/screens/order_detail_screen.dart` — `_StarPicker` now gives each of the five buttons an equal `Expanded` share of the row (padding zero, the 30dp star unchanged), so a 232dp content box holds five 46.4dp buttons instead of five 48dp ones. ## Buyer package rename finished, and the release build can reach the network

## Rider Google sign-in refused: the APK is signed with an unregistered key

The released `vendo-rider.apk` (`rider-v1.0.0`) fails **Continue with Google** with a client-configuration message, while the Buyer app on the same phone works. Measured from the published file rather than guessed:

- The embedded `libapp.so` also lacks the login screen's current failure text, so this APK was built from an earlier revision than `devv`.

Fix is Console-side and needs no rebuild: add package `vendoph.rider` + SHA-1 `C9:86:…:4F:5A` to project `468116080938`, then put the new client ID in the API's `GOOGLE_ANDROID_CLIENT_ID` (the token's `azp`) and clear the config cache. The exact steps are in `docs/features/rider-app-release.md` under **Signing key and Google sign-in**; `docs/security.md` now records why a second signing key needs a second OAuth client.
