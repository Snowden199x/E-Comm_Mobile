# Progress — 30 October 2026

## In-app notification banner and unread badge

- Added `vendo_rider/lib/core/notifications/rider_notification_center.dart`. `RiderNotificationCenter` polls `GET /api/v1/rider/notifications` every 25 seconds while the dashboard is mounted, and again when the app resumes from the background. After the first poll it sends `since=<highest id already seen>`, so the server returns only newer rows.
- Added `vendo_rider/lib/features/dashboard/widgets/rider_notice_banner.dart`. New unread items slide in over the top of every dashboard tab and can be dismissed with the close button. Tapping an assignment banner (`rider_task_assigned`) opens the Parcels tab, where the work can be started; any other banner opens the Notifications tab.
- `navigation_bar.dart` now owns the center's start/stop lifecycle, wraps the dashboard in a `Stack` so the banner sits above the tabs, and shows an unread count badge on the Notifications nav item. The Parcels tab now exposes `refreshAssignments` and reloads when selected, so an assignment that arrived while the rider was on another tab is not stale.
- `notifications_screen.dart` now feeds the shared center: loading the list adopts the server unread count, and marking one or all read updates the badge and clears the matching banner immediately.
- `rider_api.dart` `riderNotifications` accepts an optional `since` and sends it as a query parameter. Request/response shapes and the existing read endpoints are unchanged.
- First-poll behavior: only an unread notification created in the last 10 minutes raises a banner. Older unread items wait in the Notifications list, so signing in does not replay stale assignments as if they just happened. Offline or signed-out polls fail silently and retry on the next tick.

**Verified:** `flutter analyze` reports no issues in the new files or in `navigation_bar.dart`/`notifications_screen.dart`; the 12 remaining warnings/info messages are pre-existing in login, register, home, profile, splash and shared widgets. No build, device run, or widget test was performed; the polling interval and banner are owner-verifiable on a real phone.

**Known gaps**

- Polling is not push: a closed app receives nothing until it is opened.
- The banner opens the Notifications tab, not the specific parcel. Notification rows do not carry a mobile deep link.
- The Notifications tab still refreshes on tab selection and pull-to-refresh; the poll only updates the badge and banner state.

## COD cash on hand on Earnings

- Added `RiderApi.riderCash()` for the existing authenticated `GET /api/v1/rider/cash` endpoint. It returns `summary.cash_on_hand`, `summary.parcels_on_hand`, and up to 100 recent collections with order number, amount, collected-at and money status.
- `EarningsScreen` now has a **Cash on hand** section between accrued earnings and recent hub earnings. It shows the amount and parcel count, labels it plainly as buyer COD cash the Rider is holding (not pay), and explains that it leaves the total when the Station Hub records receipt. A "Recent COD collections" list shows each order, date, amount and a rider-facing status chip: `Still with you`, `Received by station`, or `Discrepancy`.
- The cash request runs alongside the earnings request. A cash failure shows a small inline retry instead of hiding earnings. Transport Driver mode hides the whole section because drivers do not collect COD.
- `DeliveryDetailScreen` now shows a **Collect ₱X cash** card from the on-the-way-to-buyer stage onward when the assignment returns `cash_collection_required`. It states the buyer pays the exact amount and that the amount is entered in the proof form; the existing proof dialog still enforces it and the server rejects a mismatch with 422.
- No backend change and no new dependency: the endpoint and station receipt already exist. `flutter analyze` reports no issues in the changed files (the same 12 pre-existing warnings/info remain). No build or device run was performed; owner device verification remains.

**Known gaps**

- Cash handover history is the same recent-collections list; there is no separate remittance-batch view in the app.
- The cash endpoint returns money statuses, not a Station receipt note or discrepancy resolution text.

## Inline proof of delivery, buyer map, call and SMS

- Removed `_DeliveryProofDialog` and `_collectDeliveryProof` from `delivery_detail_screen.dart`. The proof form is now an inline card on the parcel page: recipient name, a camera or gallery photo with preview, and the COD cash field when `cash_collection_required` is true. `Take photo`, `Choose`, `Retake` and `Remove` all act in place; nothing is modal.
- The form is validated before the scanner opens. A missing recipient, photo, or exact cash shows a snackbar and scrolls the form into view, so the Rider does not scan and then get stuck. A completed form is sent with the existing `submitDeliveryProof` call and the persisted UUID, then cleared after success.
- Added a buyer-pin map to the detail page using the existing `flutter_map`/`latlong2` dependencies and OpenStreetMap tiles. The preview is non-interactive so it does not fight the page scroll, carries the required OSM attribution, and has an **Open map** action that pushes the existing `MapScreen` with live Rider position and route line. If the buyer did not share a pin, the card says so; no coordinates are invented.
- Added call and SMS buttons to the recipient/seller card using `url_launcher` 6.3.3. Call opens the device dialer with `stop.phone` pre-filled. SMS opens the messaging app with the prefilled company template: logistics name and tracking, Rider name, COD amount from `cash_to_collect`, the photo-proof note, and the closing line. Pickup contacts get a short collection message instead of a COD reminder. The buttons only appear when the assignment includes a phone number.
- Added the dependency and platform plumbing: `url_launcher` in `pubspec.yaml`/`pubspec.lock`; Android package-visibility queries for `tel`, `sms` and `smsto`; iOS `LSApplicationQueriesSchemes` for `tel` and `sms`.
- No backend change and no migration. `flutter analyze` reports no issues in the changed files (the same 12 pre-existing warnings/info remain), and `flutter build apk --debug` completed successfully. No device run: the dialer, SMS app, photo picker, and map tiles still need owner verification on the phone.

**Known gaps**

- The call button opens the dialer; it does not place the call silently, which would need the sensitive Android `CALL_PHONE` permission and an OS prompt.
- `sms:` prefill depends on the device's default messaging app; some Android SMS apps ignore the `body` parameter.
- The map uses OpenStreetMap tiles directly and needs internet; it is a preview, not turn-by-turn navigation.

## Delivery window cutoff and reschedule

- `DeliveryDetailScreen` now shows a delivery window card from the assignment API's `delivery_window` payload: **Deliver before 5:00 PM** with the deadline, **Scheduled for &lt;date&gt;** after a reschedule, and **Delivery window closed** after the cutoff.
- A failed parcel no longer disappears: a new `RiderStage.deliveryFailed` keeps it in the Parcels list with a **Failed** filter chip and status badge. The detail page's primary action becomes **Reschedule for tomorrow** (with a confirmation dialog), which calls `POST /api/v1/rider/deliveries/{order}/reschedule`, shows the server message, and refreshes the parcel.
- For a parcel booked for a later day, the scan-out button is disabled and labelled **Scheduled for &lt;date&gt;**, and the action section explains to scan it out that day. The web API rejects the same scan, so this is not only a UI guard.
- `RiderApi.rescheduleDelivery(orderId)` added. No new dependency and no native change, so restarting `flutter run` is enough; hot reload cannot pick up the new method.
- `flutter analyze` reports no issues in the changed files (the same 12 pre-existing warnings/info remain). No build or device run was performed.

**Known gaps**

- The app has no background timer; the failed state appears on the next Parcels load or refresh.
- Rescheduling always books tomorrow. There is no date picker and no same-day retry before 5:00 PM.
- The confirmation dialog and window card still need owner verification on the phone.

## Driver API connection: session restore and password reset

- `lib/core/api/driver_api.dart` now speaks the same auth surface the Rider and Buyer clients use:
  `me()` (`GET /api/v1/transport-drivers/me`), `sendPasswordResetCode`,
  `verifyPasswordResetCode` and `resetPassword`. The signed-in profile is stored with the token so a
  restart can show the real driver, and `DriverApiException.isUnauthenticated` marks a rejected
  token so the app can clear it instead of retrying.
- `lib/features/auth/screens/driver_start_screen.dart` is the new entry point (`main.dart`). No token
  goes to sign-in; a token is checked with `me()` before the shell opens, so a revoked token, a
  suspension or an expired licence returns to sign-in. When the web cannot be reached the last
  stored profile is used rather than forcing a password re-entry.
- `lib/core/data/driver_store.dart`: `profile` is now replaceable and `applySession()` maps the API
  payload (`driver`, `province_hub`, `station_hub`, `company`) into it, including the linked Station
  Hub and the *Applied to* scope. A missing licence expiry is treated as expired rather than valid.
  Trip data, legacy credits and the depart/arrive rules are unchanged and still demo-only.
- `lib/features/auth/screens/forgot_password_screen.dart` adds the three-step recovery flow (email,
  six-digit code, new password twice) in the driver app's own style, with the email pre-filled from
  the sign-in screen. `driver_login_screen.dart` links it, clears the password field, and reports
  success when the reset returns. Sign-in now also seeds the store from the login response.
- `lib/features/profile/screens/driver_profile_screen.dart` shows the Station Hub and area and the
  *Applied to* row when the web supplies them, and the footer no longer says the build has no server
  connection.
- No new package and no migration on the mobile side; the web repo gained `GET /me` and the three
  password routes in the same session.

**Verified:** `flutter analyze` in `vendo_driver` -> No issues found. The web endpoints were checked
live with the Laravel server running (`/me` 401 without a token and a full payload with a temporary
approved driver, which was removed afterwards; reset send/verify/reset return 200/422/422). No
build, device run, widget test or app walkthrough was performed; the owner tests on a device.

**Known gaps**

- Trip, manifest, dispatch, handover and earnings screens still read demo data. Only the auth and
  profile path is live.
- Recovery needs the web to actually send the email; the app shows the same neutral message when
  delivery fails.
- The offline start path trusts the stored profile until the next successful `me()`; it does not
  queue work or retry in the background.
