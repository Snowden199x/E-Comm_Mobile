# Progress — 29 October 2026

## Philippine mobile-number format in Rider and Buyer registration

- Rider and Buyer registration phone fields now accept digits only and cap input at 11 characters. Both require `09` followed by nine digits before proceeding.
- Rider API registration enforces the same format; the corresponding Web Buyer, Seller, Logistics, Rider, Buyer API, and Transport Driver registration endpoints were updated in E-Comm_Web.
- No migration or new dependency. Flutter compile/device behavior was not run; owner verification remains pending.

## Rider deliveries screens consolidated

- Replaced the sample data in `vendo_rider/lib/features/dashboard/screens/deliveries_screen.dart` with the authenticated `GET /api/v1/rider/assignments` work list. The Parcels tab now shows real assigned parcels, stage filters with counts, the Rider's hub/vehicle context, and truthful loading, empty, and error states (including last-loaded data with a retry banner).
- Rewrote `vendo_rider/lib/features/dashboard/screens/delivery_detail_screen.dart` to open the selected assignment instead of the hardcoded `#VD-00125` sample. It now shows the server route (seller → origin hub, dispatch station → Buyer, or ordered Truck facility stops), the stop/contact details, and the currently available scan, delivery-proof, and task-issue actions.
- Moved the scan workflow (`pickup`, `origin_arrival`, `out_for_delivery`, `delivered`, Truck `facility-scans`), private delivery proof, stable scan UUIDs, and the Android/iOS/Linux label scanner out of `features/work/screens/rider_work_screen.dart` into the detail screen, then deleted `features/work/screens/`.
- `features/work/screens/transport_driver_screen.dart` was moved unchanged to `features/transport_driver/screens/transport_driver_screen.dart` so deleting the work folder would not break the Transport Driver login link; `login_screen.dart` now imports the new path.
- `navigation_bar.dart` now places `DeliveriesScreen` in the Parcels tab.

## On the way after pickup

- A pickup assignment with server status `picked_up` is now presented as **"On the way to \<origin hub>\"** in the delivery list and as a highlighted banner in the detail screen, with the instruction to bring the parcel to that hub for sorting. The detail screen also enables the existing `origin_arrival` scan at that hub.
- The same treatment names the Buyer after `out_for_delivery`, and the next server-provided facility/checkpoint for Truck linehaul. No destination, hub, or stage is invented: all names come from the assignment response (`pickup_center`, `stop`, `dispatch_facility`, `planned_route`).
- `home_screen.dart` now uses the same stage badge and headline for its Active Delivery card, so the Home tab also reads "On the way to <hub>" after a pickup scan instead of the raw `picked_up` status.
- Status wording is derived from the server status only; the app does not mark a stage complete without a successful scan or refreshed assignment.

## Hardcoded rider values removed

- Audited the Rider screens for displayed sample data. The remaining hardcoded value was the Earnings subline `₱10 per eligible hub` in `vendo_rider/lib/features/dashboard/screens/earnings_screen.dart`. The web now accrues one Rider payment per delivered parcel for newer orders and legacy per-stop shares for older orders, so a fixed rate was wrong.
- The subline now shows only the server `hub_credits` count and states that amounts are accrued from completed deliveries. Layout, styles, and the rest of the Earnings screen are unchanged.
- No other hardcoded parcel, customer, address, amount, or rate values remain in the Rider screens: Deliveries and Parcel Details read `GET /api/v1/rider/assignments`; Home stats, active parcel, and accrued total; Map destination; Earnings rows; and Transport Driver trips all call their authenticated APIs. Profile name, hub, and vehicle come from the login response stored in secure storage; the web API has no Rider profile endpoint to refresh them from. Remaining strings such as "Address unavailable" or "Assigned parcel" are empty-data fallbacks, not sample values.
- `features/dashboard/widgets/shared_widgets.dart` still contains the old `DeliveryData` model and unused widgets, but nothing renders it. `features/scanner/screens/parcel_scanner_screen.dart` is also unused. They were left in place to avoid unrelated cleanup.
- `flutter analyze` reports no new issues (the same 10 pre-existing warnings/info messages in login, register, home, profile, splash, and shared widgets). No tests, build, or device run was performed.
