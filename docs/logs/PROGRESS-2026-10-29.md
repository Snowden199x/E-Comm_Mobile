## Delivery proof submit no longer crashes the frame

- Submitting proof of delivery raised `A TextEditingController was used after being disposed`, followed by a `RenderFlex overflowed by 99592 pixels` error, the framework assertion `'_dependents.isEmpty': is not true` in `package:flutter/src/widgets/framework.dart`, and `Tried to build dirty widget in the wrong build scope`, leaving a red error screen instead of saving the proof.
- Cause: `vendo_rider/lib/features/dashboard/screens/delivery_detail_screen.dart` created the form's `TextEditingController` inside `_collectDeliveryProof` and disposed it in `finally`. `Navigator.pop` completes the `showDialog` future while the dialog route is still animating out, so the still-mounted `TextField` rebuilt against a disposed controller.
- The confirmation and task-issue forms are now the private `StatefulWidget`s `_DeliveryProofDialog` and `_TaskIssueDialog`, which own their controllers and dispose them when the dialog route is actually gone. `_reportTaskIssue` and `_collectDeliveryProof` only await the result, so `_reportTaskIssue` had the same latent crash on its Cancel path and is fixed with it.
- Labels, validation (recipient name of 2+ characters, 5 MB photo limit, 5+ character issue details) and the `delivery-proofs` / `tasks/{id}/exceptions` calls are unchanged. The camera-error snackbar now runs inside the dialog where the capture happens.
- Verified: `flutter analyze` reports no issues in the file; the debug APK was rebuilt with `VENDO_API_BASE_URL=http://192.168.0.113:8001/api/v1/rider`, installed, and starts with no framework exception. A real proof submission was not run end to end because the phone must be on the same Wi-Fi as the API and a physical label must be scanned.

## Delivery proof now reports COD cash so the parcel reaches delivered

- Submitting proof for a COD parcel was rejected by the web API with 422 `Enter the exact cash collected: ...`, so no proof, no scan, and no delivered status were saved. The Rider app never sent `cash_collected`, which the API requires whenever the order's `money_status` is `not_collected`.
- `rider_api.dart` `submitDeliveryProof` now accepts an optional `cashCollected` and posts it as `cash_collected` formatted to two decimals.
- `delivery_detail_screen.dart` reads `cash_collection_required` and `cash_to_collect` from the assignment and passes the amount into `_DeliveryProofDialog`. The dialog shows the cash due, asks the Rider to type it, keeps Submit disabled until it matches the COD total to the centavo, and returns it with the recipient name and photo.
- The success snackbar now says the parcel is delivered for the buyer, seller, and station hub. Order status, `delivered_at`, the Rider delivery task, the COD collection row, the shipping-earnings accrual, and the buyer/seller/hub notifications are all written by the existing web API transaction; the mobile app sends one request.
- Verified with `curl` against the local API using the app's exact payload: `VND-01M63MJPNV0RBTZZD3H3NA0Y2G` moved to `delivered`, `money_status` `collected_by_rider`, proof row and COD collection saved, delivery task completed, settlement accrued (Rider PHP 10.00), and notifications created for the buyer, seller, and destination logistics center. That test order is now delivered; `VND-01M63YVGC82MGK0Q4RG5NDVEZ3` remains out for delivery for an app-side run. `flutter analyze` reports no issues.
