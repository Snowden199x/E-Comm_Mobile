# Progress — 15 November 2026

## The destination handover follows the hub's scans while it is open

The driver's **Receiving progress** read the trip once, when the screen opened, so a parcel the destination hub scanned afterwards did not move the count or leave the "Awaiting station scan" list until the driver went back and reloaded the board. The driver could not tell which parcels still needed a scan.

- `driver/core/api/driver_api.dart` — `trip(tripId)` reads `GET /api/v1/transport-drivers/trips/{id}` through the same authorized GET as the board, so a rejected token is reported exactly like the other driver calls.
- `driver/core/data/driver_store.dart` — `refreshTrip(tripId)` puts the answered trip back on the board through `_replaceWithApiTrip`, which is the same path the depart, scan and arrive answers already used. It never touches `tripsLoading`, so a background poll cannot flash the board's spinner, and a failure leaves the last counts on screen instead of clearing them.
- `driver/trips/screens/driver_handover_screen.dart` — the screen now re-reads its trip every 10 seconds while it is open, once more when the app returns to the foreground, and immediately on open. A small line under the progress bar says how fresh the count is (*Updated just now*, *Updated 12s ago*, *checks the hub every 10s*), with a spinner while a read is in flight. The *Awaiting station scan* list is now built from each parcel's `destination_scanned` flag instead of assuming the first N are done — the hub can scan in any order — and it lists every parcel still waiting rather than the first five, since that list is the driver's handover checklist. Sample (non-live) trips keep the simulated scan button and are labelled as samples.
- The blocked sheet no longer tells the driver to pull to refresh; it says the screen follows the station's scans as they happen.

## Both apps sign with one committed debug keystore

Google sign-in on the phone failed with `[28444] Developer console is not set up correctly`, which is Google's `DEVELOPER_ERROR`: the installed app's package plus signing certificate matched no Android OAuth client in the project that owns the `GOOGLE_WEB_CLIENT_ID` the app passes as `serverClientId`. Every contributor's `~/.android/debug.keystore` is a different key, so each machine produced a different app identity and no single registered SHA-1 could cover them.

- `android-keys/vendo-debug.keystore` — new, committed on purpose. Public debug-only key (alias `androiddebugkey`, password `android`, RSA 2048, valid to 2056), SHA-1 `DC:3B:DF:DA:36:47:2F:8C:4D:2A:46:6F:BB:F1:FF:E4:F5:62:8E:C9`. It is not an upload key and must never sign a Play release.
- `vendo_buyer/android/app/build.gradle.kts` — a `vendoDebug` signing config reads the shared file through `rootProject.file("../../android-keys/vendo-debug.keystore")`; the `debug` build type uses it, and `release` keeps its previous "debug key for now" behaviour by pointing at the same config.
- `vendo_rider/android/app/build.gradle.kts` — the same `vendoDebug` config; `debug` uses it, and `release` falls back to it only when `android/key.properties` is absent, so a real upload key still wins when present.

## Both packages go into the web client's Google Cloud project

Decision: instead of moving the whole setup to `vendo-mobile-514813`, the two Android OAuth clients are registered in `468116080938` — the project that already owns the web client the apps send as `serverClientId` and the website's authorized origins. No app code changes for this: both configs already default to that web client.

- The web API's `GOOGLE_ANDROID_CLIENT_ID` now accepts a comma-separated list of Android client IDs, one per package, and feeds them into `allowed_client_ids`. A Credential Manager token carries the package's Android client as `azp` and the web client as `aud`, and the verifier checks both, so both IDs have to be allowed. The config change and its verification are recorded in the web's `docs/logs/PROGRESS-2026-11-15.md`.
- Owner-only Console work remains: create an Android OAuth client for `com.example.vendo_buyer` and one for `vendoph.rider`, each with SHA-1 `DC:3B:DF:DA:36:47:2F:8C:4D:2A:46:6F:BB:F1:FF:E4:F5:62:8E:C9`, then put both IDs into the web `.env`.
