# Progress — 13 November 2026

## Buyer Android build toolchain upgrade (Gradle 9 / AGP 9 / Kotlin 2.4)

`flutter run` on `vendo_buyer` failed the same way `vendo_rider` did the day before, before any Dart code was compiled:

- `Error: Your project's Gradle version (8.14.0) is lower than Flutter's minimum supported version of 9.3.1` (raised from `android/app/build.gradle.kts` when applying `dev.flutter.flutter-gradle-plugin`)

The local Flutter SDK is 3.50.0, which requires Gradle >= 9.3.1 and AGP >= 9.1.1. `vendo_buyer` was still on the template defaults (Gradle 8.14 / AGP 8.11.1 / Kotlin 2.2.20), so the same upgrade applied to `vendo_rider` was applied here. No Dart code, manifest, applicationId (`com.example.vendo_buyer`) or build types were touched.

### Changed files (`vendo_buyer/android/`)

- `gradle/wrapper/gradle-wrapper.properties` — Gradle `8.14` -> `9.5.0`.
- `settings.gradle.kts` — `com.android.application` `8.11.1` -> `9.1.1`, `org.jetbrains.kotlin.android` `2.2.20` -> `2.4.0`.
- `app/build.gradle.kts` — the `android { kotlinOptions { jvmTarget = ... } }` block is not supported by AGP 9 / Kotlin 2.4, replaced with a top-level `kotlin { compilerOptions { jvmTarget = JvmTarget.JVM_17 } }` block (same shape as `vendo_rider` and `vendo_driver`). Remaining content unchanged.
- `gradle.properties` — `org.gradle.jvmargs` lowered from `-Xmx8G -XX:MaxMetaspaceSize=4G` to `-Xmx3072m -XX:MaxMetaspaceSize=1024m -XX:ReservedCodeCacheSize=256m`, so the Gradle daemon fits in this 7 GB-RAM machine (the 8 GB heap crashed the daemon during the rider build on 12 Nov).

### Verified

- `flutter build apk --debug --dart-define=VENDO_BUYER_API_BASE_URL=http://192.168.1.17:8001/api/v1/buyer` in `vendo_buyer`: succeeded, Gradle `assembleDebug` took ~1167 s on this machine, produced `build/app/outputs/flutter-apk/app-debug.apk` (159.7 MB, debug).
- Not run: install/launch on the Infinix X6831, `flutter run` hot reload, release build, `flutter analyze`. The owner tests on device.

### Known gaps / next steps

- Same forward-looking warnings as `vendo_rider`: AGP should reach 9.3.1 and Kotlin 2.4.20 eventually, and `app` still applies the Kotlin Gradle Plugin instead of built-in Kotlin. Warnings only, build succeeds.
- Buyer and rider `android/gradle.properties` share identical memory settings; raising them again is only worthwhile on a machine with more RAM.

## Google sign-in in the Buyer and Driver apps

The Rider app already signed in with Google; the Buyer app showed a "Google sign-in coming soon." snackbar on its existing button, and the Driver app had no button. Both now post a Google ID token to the web API, which verifies it with the same `GoogleIdTokenVerifier` the Rider and browser logins use.

### Changed files

- `vendo_buyer/pubspec.yaml`, `vendo_driver/pubspec.yaml` — added `google_sign_in: ^7.2.0` (already used by `vendo_rider`), with the resolved versions written to each `pubspec.lock` by `flutter pub get`.
- `vendo_buyer/lib/core/api/buyer_api.dart` — new `googleSignIn(idToken)` that posts `credential` and `device_name` to `$baseUrl/google` and stores the returned session with the existing `_saveLogin`.
- `vendo_buyer/lib/features/auth/screens/login_screen.dart` — the placeholder handler is replaced by `_continueWithGoogle()`: initialize `google_sign_in` with `GOOGLE_WEB_CLIENT_ID` (and the iOS/macOS client when those are passed), read the ID token, call the API, open `HomeScreen`. The button is disabled while busy and shows a spinner plus "Signing in…". Desktop keeps email/password with an honest message.
- `vendo_driver/lib/core/api/driver_api.dart` — new `googleSignIn(idToken)`, plus the token/profile writes extracted from `login()` into `_saveSession(data, email)` so both sign-ins store one session shape and a pending application raises the same `DriverApiException` with its hub name.
- `vendo_driver/lib/features/auth/screens/driver_login_screen.dart` — new `_signInWithGoogle()` and a **Continue with Google** outlined button between the *or* divider and *Check application status*, reusing the existing error/pending banner and `DriverStore.applySession`. Includes the same `_GoogleLogo` painter the Buyer and Rider screens use, so the mark keeps Google's colours.
- `docs/features/buyer-app.md`, `docs/features/driver-app.md` — documented the new flow, the required OAuth client IDs and the desktop limitation.

Web side (separate repository, see that repo's log): new `POST /api/v1/buyer/google` and `POST /api/v1/transport-drivers/google`, which apply the same role/approval checks as each app's `/login`.

### Verified

- `flutter analyze` in `vendo_buyer` and `vendo_driver`: no errors and no new warnings (only the pre-existing `withOpacity`/`material.dart` deprecation infos remain). One missing `package:flutter/foundation.dart` import found by the analyzer was fixed in both login screens.
- `flutter pub get` resolved `google_sign_in 7.2.0` in both apps.
- Not run: any device or emulator sign-in, an app build, or a real Google token exchange. Owner verification and OAuth-console setup remain.

### Follow-up after the first device attempt

The first run on the phone only showed a generic "Google sign-in could not complete" snackbar, which hid the real cause. The sign-in handlers now catch `GoogleSignInException`, ignore a user cancellation, print the plugin error with `debugPrint`, and turn a configuration failure into a message naming the missing Android OAuth client and package. A build without any client ID now says so before opening Google instead of failing inside the plugin.

The client ID no longer has to be typed on every run: `lib/core/config/google_auth_config.dart` in the Buyer and Driver apps (the Rider app followed in the section below) defaults `GOOGLE_WEB_CLIENT_ID` to the public web client the site already ships (`468116080938-...apps.googleusercontent.com`, the value in the web's `services.google.web_client_id`), and the `--dart-define` still overrides it. The debug keystore on this machine has SHA-1 `4F:80:D0:D4:D6:60:49:70:EF:CE:C0:D2:21:70:71:36:15:35:C1:84`, which is the fingerprint that must be registered against `com.example.vendo_buyer` and `com.example.vendo_driver` in Google Cloud; the rider's `google-services.json` belongs to a different Firebase project, so it supplies push only and not this OAuth client.

### Known gaps / next steps

- Google sign-in needs real configuration before it can be tried: the Android OAuth clients for `com.example.vendo_buyer`, `com.example.vendo_driver` and `vendoph.rider` plus their signing SHA fingerprints must be added to the Google Cloud project behind the default client ID (or `GOOGLE_WEB_CLIENT_ID` and `GOOGLE_ALLOWED_CLIENT_IDS` changed together for another project).
- Both apps only sign in existing accounts with Google; a new user still registers through the app's own form (the Rider app, by contrast, also accepts Google for a new application).
- iOS/macOS were not configured or tested; only Android was built on this machine.

## Google sign-in in the Rider app

The Rider app already posted a Google ID token to the API, but its client ID only arrived through `--dart-define`, and every failure (a missing ID, a canceled prompt, a missing OAuth client) collapsed into one generic snackbar. It now matches the Buyer and Driver apps.

### Changed files

- `vendo_rider/lib/core/config/google_auth_config.dart` — new; `webClientId` defaults to the public web client (`468116080938-...apps.googleusercontent.com`), with `iosClientId`/`macosClientId` from their `--dart-define` values. A `--dart-define=GOOGLE_WEB_CLIENT_ID=...` still overrides the default.
- `vendo_rider/lib/features/auth/screens/login_screen.dart` — `_continueWithGoogle()` reads `GoogleAuthConfig.*` instead of `String.fromEnvironment` inline, shows a snackbar and returns when no client ID was compiled in, catches `GoogleSignInException` (a cancellation is ignored, other codes are printed with `debugPrint`), and converts a failure through the new `_googleFailureMessage()` helper, which names the missing Android OAuth client for `vendoph.rider` and this build's SHA-1. Registration, OTP and password paths are untouched.
- `docs/features/rider-integration.md`, `docs/security.md` — the client ID is now a default rather than a required build flag, and the error behaviour is described.

### Verified

- `flutter analyze` in `vendo_rider`: 46 issues, all pre-existing infos/warnings, no errors. The one warning in `login_screen.dart` (`unused_field` on the `raisinSoft` palette constant) predates this change.
- Not run: a device sign-in, an app build, or a real token exchange. The owner tests on the phone.

### Known gaps / next steps

- Google Cloud still needs an Android OAuth client for package `vendoph.rider` with the debug SHA-1 `4F:80:D0:D4:D6:60:49:70:EF:CE:C0:D2:21:70:71:36:15:35:C1:84` (and later the release upload-key SHA-1) in project `468116080938`. Until that exists, Google rejects the request and the app reports the configuration error. The rider's `google-services.json` is from a different Firebase project, so it covers push only.
- iOS/macOS client IDs and URL schemes remain unset, and only Android was built on this machine.

## Driver Earnings tab connected to the web ledger

The Transport Driver app's Earnings tab was the last driver screen still showing demo data even though the web already exposes `GET /api/v1/transport-drivers/earnings`. It now reads that endpoint instead of the hardcoded `LegacyCredit` rows.

### Changed files

- `vendo_driver/lib/core/api/driver_api.dart` — new `earnings()` behind the existing `_authorizedGet`, so a 401 clears the session and is reported like the trip calls.
- `vendo_driver/lib/core/data/driver_store.dart` — `DriverEarning` / `DriverEarnings` models, `earnings`, `earningsLoading`, `earningsError`, `earningsSessionExpired`, `earningsSyncedAt`, and `refreshEarnings()`, which takes the server's `summary` and `earnings` arrays as-is. A successful live-trip close now reloads the ledger in the background (`unawaited` in `arrive`), so a credit from that trip does not need a manual pull. The `LegacyCredit` demo list and its totals were removed.
- `vendo_driver/lib/features/earnings/screens/driver_earnings_screen.dart` — API-backed tab with pull-to-refresh, a loading card, the server summary card (accrued total, credit count, "not a payout" note), one row per credit (order, hub, route position, date, amount), empty state, error notice with Retry, and a Sign in action when the token was rejected.
- `vendo_driver/lib/features/dashboard/screens/driver_shell.dart` — loads the earnings ledger next to `refreshTrips()` so the tab is not blank when the driver first opens it.
- `docs/features/driver-app.md`, `docs/domain-feature-status.md`, `docs/architecture.md`, `docs/README.md` — status text updated; the driver app is no longer described as UI-only or demo-only.

### Verified

- `flutter analyze lib` in `vendo_driver`: no errors and no new warnings; the only output is the pre-existing `package:flutter/material.dart` deprecation infos (20 total).
- Not run: device sign-in, a live earnings response, pull-to-refresh on a phone, or an app build. The owner tests on device.

### Known gaps / next steps

## Driver notifications and trip history

The Driver app had no way to see what the company sent it or to look back at a closed trip. The Laravel API gained `GET /notifications` (with read/read-all) and `GET /trips/history` in the same session, so this adds the app side and wires it to those endpoints; no demo rows are involved.

### Changed files

- `vendo_driver/lib/core/api/driver_api.dart` — `notifications()`, `markNotificationRead()`, `markAllNotificationsRead()` and `tripHistory()`, plus an optional fallback message on the shared authorized POST so a failed read is not reported as a failed trip.
- `vendo_driver/lib/core/data/driver_store.dart` — `DriverNotification` and `DriverTripHistoryEntry` models, notification list/loading/error/unread state with `refreshNotifications()`, optimistic `markNotificationRead()` that reverts and resyncs on failure, `markAllNotificationsRead()`, and trip-history state with `refreshTripHistory()`. Notification read state and unread counts always come from the server; the app never invents one.
- `vendo_driver/lib/features/notifications/screens/driver_notifications_screen.dart` — new feed: unread marks, tap to read, mark-all-read in the header, pull-to-refresh, loading/empty/error states and a sign-in action for a rejected token.
- `vendo_driver/lib/features/dashboard/screens/driver_home_screen.dart` — notification bell with the unread badge in the animated header; tapping it reloads the feed and opens the screen, and Home pull-to-refresh now refreshes trips and notifications together.
- `vendo_driver/lib/features/trips/screens/driver_trip_history_screen.dart` — new screen listing completed trips with route, completion time, parcels and vehicle.
- `vendo_driver/lib/features/dashboard/screens/driver_trips_screen.dart` — **Trip history** button; the "later" notice no longer promises trip history.
- `vendo_driver/lib/features/dashboard/screens/driver_shell.dart` — loads notifications with the trips and earnings when the shell opens.
- `docs/features/driver-app.md`, `docs/domain-feature-status.md`, `docs/architecture.md` — screens, navigation, status and gaps updated.

### Verified

- `flutter analyze lib` in `vendo_driver`: no errors or new warnings; only the pre-existing `package:flutter/material.dart` deprecation infos (22 now, two of them in the new screens).
- Not run: device sign-in, a driver account with real notifications, read-state changes, or the history list on a phone. The owner tests on device.

### Known gaps

- No push notifications or background polling: the feed loads when the shell opens, on Home pull-to-refresh, and when the bell is opened.
- History is capped at 50 trips with no date filter or pagination.
