# Progress — 3 November 2026

## Registration: one identity document, not two

- `vendo_rider/lib/features/auth/screens/register_screen.dart`: removed the **Valid ID** upload from step 1 (Personal Information). The Rider already uploads a driver's licence in step 2, and the licence is the identity document the station reviews, so the extra image was asking for the same evidence twice. The `_validIdFileName` / `_validIdPath` state, the `validId` entry in `_invalidIds(0)` and the `valid_id` part in the multipart body are gone, and the review card's "Valid ID" cell was dropped. `_ReviewRow4.item4` is now optional so the Contact row renders three cells instead of leaving a blank one.
- `vendo_driver/lib/features/auth/screens/driver_register_screen.dart`: same removal on step 1 — the `RegUpload` for Valid ID, its `validId` validation key, its state fields and the `valid_id` upload in the register payload. The Driver registers with the licence number, category, expiry and licence photo only.
- The Rider's step 2 (vehicle, licence, OR/CR) and the Driver's step 3 (vehicle and licence) are unchanged, so nothing the reviewer checks was lost.
- Contact number: each registration form already carries exactly one phone field, and it is the same single value sent as `phone_number` (Rider, Driver) or `contact_number` (Buyer). Nothing changed here.

**Verified:** no `validId` / `valid_id` references remain in `vendo_rider/lib` or `vendo_driver/lib`; `flutter analyze` run on both apps — results recorded in the web log for the matching API change.

**Known gaps**

- No phone build or device run: the removal was not exercised by hand, so the review step's three-cell row is only compile-checked.
- Installed copies of older builds keep sending `valid_id`; the API still accepts it, so nothing breaks for them.

## Driver: scan the load before dispatch

- `vendo_driver/lib/features/trips/screens/driver_scan_screen.dart` (new): the first step of a scheduled trip. A `mobile_scanner` camera reads QR / Code 128 / Code 39 / EAN-13, a typed tracking number does the same job when the camera is unavailable, and each parcel is ticked as it is scanned. **Confirm dispatch** is disabled until the last parcel is scanned; when it lands the button opens the existing dispatch confirmation screen, which still asks for the Depart tap. A repeated barcode is ignored for three seconds, a parcel that already carries the scan comes back as "already scanned", and a wrong number, a parcel not routed through the origin hub or a trip that already left is shown as a red answer under the field.
- `driver_trip_details_screen.dart`: the bottom action on a scheduled trip is now **Scan parcels · X of N** instead of **Confirm dispatch**, and a notice card explains that dispatch opens after the last scan. In transit and completed trips keep their existing actions.
- `driver_home_screen.dart`: the Dispatch quick action became **Scan load** (X of N scanned) and the current-trip card button opens the scan screen. `driver_manifest_screen.dart` ticks parcels by tracking number, so a partial load shows the parcels that really are on the truck.
- `core/api/driver_api.dart`: `scanParcel(tripId, trackingNumber, scanKey)` posts to the new endpoint and returns the trip plus `duplicate` and the server message.
- `core/data/driver_store.dart`: `DriverTrip` keeps the scanned tracking numbers behind `origin_scanned` / `destination_scanned` (`originScanRecorded`, `destinationScanRecorded`, `stageFor(tracking)`), and `scanLoadParcel` records a scan. A live trip takes the trip the server returns; a sample trip keeps the scan on the device and first turns its seeded count into tracking numbers so earlier ticks are not lost. `_scanKey()` builds a v4 UUID with `Random.secure`, so a retried tap is not recorded twice.
- `mobile_scanner ^7.4.2` (the version the Rider app already uses) added to `pubspec.yaml`, the CAMERA permission to the Android manifest, and the iOS camera description widened to cover parcel barcodes.

**Verified:** `flutter pub get` → resolved; `flutter analyze` → **No issues found**.

**Not run:** no device or emulator run, so the camera preview, torch and the scan loop are compile-checked only; no HTTP call was made against a seeded trip. The backend half is logged in `E-Comm_Web/E-Comm_Web/docs/logs/PROGRESS-2026-11-03.md`.

**Known gaps**

- The destination side is unchanged: the station scanner records the receiving scans, so the driver cannot close a trip on their own.
- The camera stays open only while the scan screen is mounted; no background scanning and no offline queue for scans.
- Scans are one parcel at a time, so a 40-parcel load is 40 scans.

## Driver: container labels load several parcels in one scan

- `driver_scan_screen.dart` now parses what the label actually carries instead of assuming one tracking number: a plain code, a list separated by commas / semicolons / pipes / spaces / line breaks, an optional scheme prefix (`VENDO-CONTAINER:` and similar), a JSON list or `{"tracking_numbers": [...]}`, and the trip's own QR (`TRP-00042`) as the whole manifest. Tokens shorter than five characters or containing anything other than letters, digits and dashes are dropped, duplicates collapse, and a payload with no usable code gets its own red message.
- `core/data/driver_store.dart`: `scanLoadParcels(trip, codes)` replaces the single-parcel call (`scanLoadParcel` is now a one-code wrapper). It drops codes that are not on the manifest, skips parcels already scanned, and sends only the pending ones in one request. `LoadScanResult` gained `scanned`, and `_scanMessage()` writes the "N parcels scanned. X of Y on board." / "already scanned" / "not on this manifest" sentence used for sample trips and for a server answer with no message.
- `core/api/driver_api.dart`: `scanParcels(tripId, trackingNumbers, scanKey)` posts `tracking_numbers` and reports how many the server recorded.
- The scan screen explains the two label kinds under the viewfinder and shows one tick per parcel after a container scan.

**Verified:** `flutter analyze` → **No issues found**.

**Not run:** no device run and no HTTP call; a container QR has not been scanned on a real camera, and the label format is only exercised through its parser and the API contract.

**Known gaps**

- A container label is a list of tracking numbers, not a stored container: the parcels are not grouped in the database and a container code cannot be looked up later.
- A label with more than 100 tracking numbers is trimmed to the first 100 on the client and the server.
- A container scan still writes one departure scan per parcel, so a 40-parcel bag is 40 rows and 40 focus/insert operations in one transaction.

### Fix: red screen on the scan screen

`DriverTrip` initialised its two scanned-tracking sets in a constructor initializer list with parameters named after the fields. On device the field was read as `null` and the implicit getter threw `type 'Null' is not a subtype of type 'Set<String>' of 'function result'`, so the load scan screen opened on Flutter's red error page instead of the camera. The sets are now declared with `<String>{}` defaults and only replaced in the constructor body when a value is passed, so every trip always exposes a set. Confirmed with a temporary test (constructor defaults, per-parcel ticking, count-only fallback) that was removed afterwards, and `flutter analyze` stays clean. The app needs a full rebuild — hot reload does not pick up a changed constructor signature.

### Scan screen: camera start has a deadline

The camera is now started by the screen (`autoStart: false`, started after the first frame) with an eight-second timeout. A wedged CameraX start used to leave the viewfinder on "Starting the camera…" forever; it now switches to a panel that says the camera is taking too long, offers **Try again** (stop, then start), and points at the typed tracking-number field. Plugin errors keep their own message — permission denied, unsupported device, camera in use — through `errorBuilder`, and the torch button is hidden while the camera is not running. The installed APK must include the new CAMERA permission, which only a fresh build (`flutter run` / reinstall) applies, not hot reload or hot restart.

**Verified:** `flutter analyze` → **No issues found**. Not run on a device, so the eight-second window is a judgement call rather than a measured one.
