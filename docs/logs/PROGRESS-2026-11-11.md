# 11 November 2026 — Rider app return leg

## What changed

- `vendo_rider/lib/features/dashboard/screens/delivery_detail_screen.dart`: new `RiderStage.returnPickup` / `RiderStage.returnHandover` derived from the API's `assignment: return` and `return.status`; stage badges ("Return pickup", "Return to seller"), titles/subtitles, contact card (Buyer while collecting, Seller after), delivery-pin map only for the pickup step, return-specific scan labels and messages, and SMS wording. `riderScanTypeFor` now returns `return_pickup` / `returned_to_seller`; the scan flow posts to the return endpoints and queues them offline with the order id.
- `vendo_rider/lib/core/api/rider_api.dart`: `returnPickup()` and `returnHandover()` call `POST /api/v1/rider/deliveries/{order}/return-pickup|return-handover`; `queueScanOffline` accepts an `orderId` and the sync loop replays return scans through those endpoints.
- `vendo_rider/lib/features/dashboard/screens/deliveries_screen.dart`: **Return** filter, return stage styles, and the Delivery summary tile counts return tasks.
- Web API: `GET /api/v1/rider/assignments` now returns the approved return leg (`assignment: return`, `return` block, Buyer→Seller stop, `summary.return`). Documented in the web repo's scan API and return request specs.

## Why

The web app now has an approved return trip (Buyer asks, Seller approves, Rider collects and hands back). The Rider app previously had no return task, so the parcel would never come back through the app.

## Verified

- `flutter analyze` in `vendo_rider`: no errors (only pre-existing warnings/infos).
- Not run: device walkthrough, scanner, offline replay or a live approved return. The owner tests those.

## Known gaps

- Truck linehaul riders do not receive return tasks.
- Return history is not shown in History; the parcel leaves the active list after handover.
- No push notification when a return is assigned; the Parcels list updates on refresh/notification poll.


## Rider push notifications (FCM)

- Added `firebase_core` and `firebase_messaging`.
- `lib/core/push/rider_push_service.dart`: guarded Firebase init (build-time `--dart-define` options or platform files), permission request, token registration and refresh, foreground feed refresh, tapped-push refresh, and `reset()` on sign-out.
- `lib/core/api/rider_api.dart`: `registerPushToken()` / `removePushToken()` against `POST|DELETE /api/v1/rider/push-tokens`; logout removes the token first.
- `lib/main.dart` registers the background handler; `navigation_bar.dart` starts push after sign-in and resets it on dispose. Android manifest adds `POST_NOTIFICATIONS`.
- Server side (web repo): `push_devices`, push-token endpoints, `FirebasePushService` and a queued job triggered by courier notifications.

**Verified:** `flutter analyze` — no errors (only pre-existing warnings/infos, plus two info-level deprecation notices for `getToken`/`onTokenRefresh`, which still return the FCM registration token the HTTP v1 sender needs). **Not run:** device install, permission prompt, push delivery or token cleanup. `flutter build apk --debug` compiles cleanly with the project's JDK 21 (`.tooling/jdk-21.0.13+9`); build without `JAVA_HOME` still fails on system Java 25 vs Gradle 8.14.

### Firebase Android config

- `google-services.json` (project `vendorider`, package `vendoph.rider`) moved to `android/app/google-services.json`, and the `com.google.gms.google-services` plugin (4.4.3) added to `android/settings.gradle.kts` + `android/app/build.gradle.kts`. Builds no longer need `--dart-define` for Firebase; runtime options override the file only if supplied.
- Verified: `flutter build apk --debug` succeeds with JDK 21, and the merged resources contain `google_app_id`/`gcm_defaultSenderId`/`project_id` from the file. Not verified: an actual push (web still needs the service account for project `vendorider`).
- `android/app/google-services.json` is now gitignored (`.gitignore`), since it is project-specific; fresh clones need their own copy or `--dart-define` options.
