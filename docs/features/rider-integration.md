# Rider registration and parcel scans

**Status:** Rider auth/registration, API-backed assigned-work screens, in-app notifications, COD cash-on-hand, inline delivery proof, buyer map, call/SMS shortcuts, and the daily delivery window with reschedule are connected; owner verification is pending
**Updated:** 30 October 2026

## Registration

Phone input is numeric-only and limited to 11 digits. Before continuing, registration requires Philippine mobile format `09` followed by 9 digits; the Laravel Rider and Transport Driver registration APIs enforce the same rule.

The rider selects a province and municipality/city from the web app's PSGC snapshot, then a searchable barangay list loaded from `GET /api/v1/rider/locations/{cityCode}/barangays`. The app submits all three location codes, personal details, a Motorcycle, Van, L300, or Truck vehicle, a valid ID, driver license, and OR/CR image as multipart form data. The API verifies that the barangay belongs to the chosen city and the city belongs to the province, then chooses a unique approved active hub: exact city when unique, otherwise unique province. No arbitrary center or GPS-distance fallback exists. Unmatched or ambiguous addresses return a validation error and do not create an application. The created Rider account is pending and appears in that center's Rider Management queue. The center approves or rejects it in the web app.

Before the app submits a Rider application, it must verify the email using the API's six-digit email OTP or a short-lived Google registration proof returned after server-side Google ID-token verification. Both proofs are bound to the normalized email, expire, and are consumed after successful registration. Google newcomers continue into the same application form with name/email prefilled; Google only replaces email OTP and does not skip password, profile, address, private documents, hub matching, or Logistics approval.

The app cannot guarantee that a chosen hub is physically closest. Hub coverage and reassignment rules need separate operational decisions. Identity images are uploaded to private server storage; the hub reviewer currently has no dedicated authorized document download screen.

## Authentication and assigned work

Only approved active Riders attached to approved active centers can log in with a password or Google. The API verifies Google ID tokens and issues the same seven-day Rider bearer token; pending accounts still need Logistics approval. Forgot Password emails a one-time code, exchanges a valid code for a short-lived reset proof, changes the password, and revokes existing Rider API tokens. The token, Rider name, center name, and registered vehicle type are stored in platform secure storage. Motorcycle, Van, and L300 accounts use local pickup/delivery assignments; legacy Truck accounts receive assigned facility linehaul work. Successful password and Google login open the five-tab `DashboardScreen`. Its Home shows live assignment totals and the first active assigned parcel from `GET /api/v1/rider/assignments`; returning from Parcels refreshes those values. The Parcels tab is the API-backed `DeliveriesScreen`, which lists assigned stops with a server-derived stage and opens `DeliveryDetailScreen` for the route, contact, and available scans. After a `pickup` scan the assignment stays in the list as "On the way to <origin hub/sub-station>" and the detail banner names that next hub; the same treatment points a delivery at the Buyer after `out_for_delivery`. Earnings reads accrued shipping-earnings lines from `GET /api/v1/rider/earnings`; Home displays the API total and the Earnings tab lists recent credits. The web rule is one per-parcel Rider payment for newer orders and legacy per-stop shares for older orders, so the app shows only the server count and amounts and does not state a fixed rate. These amounts are accrued, not payouts. The former Map screen remains in source but is no longer reachable from dashboard navigation; that tab now opens Notifications as described below. Profile shows stored Rider, hub, and vehicle details and calls the API logout endpoint.

The Rider dashboard's former Map tab is replaced by a Notifications tab backed by the authenticated `GET /api/v1/rider/notifications`, `POST /notifications/{id}/read`, and `POST /notifications/read-all` endpoints. It lists only the signed-in Rider's notification rows, supports pull-to-refresh and mark-all-read, and does not invent updates the server has not sent.

While the dashboard is open, `RiderNotificationCenter` polls the feed every 25 seconds and again when the app resumes from the background. It remembers the highest notification id it has already seen (`?since=<id>` asks the server for newer rows only), so the same notification is not announced twice. New unread items raise a dismissible banner over the top of every dashboard tab, and the Notifications tab shows an unread count badge. Tapping an assignment banner opens and reloads the Parcels tab, where the new work can be started; other banners open Notifications. The Parcels tab now also reloads whenever it is opened, so an assignment that arrived while the rider was elsewhere is present. On the first poll after sign-in, only an unread notification from the last 10 minutes raises a banner, so older items wait in the list instead of appearing as if they just happened. Marking items read on the Notifications tab updates the shared badge immediately.

A Rider is notified when a Station Hub assigns a pickup or delivery task, when a Main Hub assigns a pickup, delivery or Truck linehaul parcel, and when a Station Hub pickup assignment is released after 60 unscanned minutes. This is still in-app polling, not push: a closed app receives nothing until it is opened. The map screen is no longer reachable from dashboard navigation.

For a selected assignment, the camera reads the label's QR or Code 128 barcode; both encode the same tracking number, and only an exact match with the assigned parcel is accepted. Android/iOS explicitly configure `mobile_scanner` for those two formats. Linux explicitly enables both in `zbarcam`. A matching read sends the supported `pickup`, `origin_arrival`, `out_for_delivery`, or `delivered` action according to the assignment's current server status. Legacy SOC-coded scan actions are not presented as actual SH arrivals. The `delivered` scan appears after `out_for_delivery` and should be used only after handing over the parcel; the Laravel API restricts it to the approved rider assigned for destination delivery. A UUID scan key is stored before the network call and reused if a connection fails; successful scans clear it. The Laravel API authorizes the rider and order, records the scan, and updates notifications and the seller/buyer timeline. A scan is not treated as successful merely because the camera read a code.

The web API returns assigned Truck linehaul work with ordered facility stops and a server-derived `planned_route.scan_target`. In `DeliveryDetailScreen`, the Truck Rider scans the assigned parcel label; the app submits its tracking number, server-provided facility ID, and stable UUID to `POST /api/v1/rider/facility-scans`. The backend verifies the Rider assignment and route stop, then derives the next action. A station arrival scan records receipt and sorting together; intermediate stations need a later departure scan. This does not prove truck movement or custody.

`DeliveryDetailScreen` also embeds an OpenStreetMap preview of the buyer's pin (`stop.latitude`/`stop.longitude` from the assignment API) with an **Open map** action that opens the existing `MapScreen` with the Rider's live position and route line. When the buyer shared no pin, the card says so instead of inventing coordinates. The recipient card has call and SMS buttons: call opens the device dialer with `stop.phone` pre-filled, and SMS opens the messaging app with a prefilled company-format message (`<logistics>  TN: <tracking>, Rider: <Rider name>. ...`), using the approved center's business name and `cash_to_collect` for the COD line. Pickup contacts get a short collection message instead of a COD reminder. These actions leave the app; Vendo does not send the call or SMS itself.

The web app must have the province facility schema migrations applied before the assignments include facility targets: `2026_10_14_120000_create_logistics_facilities.php` and `2026_10_14_121000_create_order_facility_scans.php`. This mobile change adds no database migration.

`delivered` remains the app's legacy handover scan for orders using the older flow. For facility-routed orders, the assignment response marks proof as required and `DeliveryDetailScreen` shows an inline **Proof of delivery** form instead of a dialog: recipient name, a camera or gallery photo with preview, and the COD cash field when the assignment requires it. The form is checked before the scanner opens, so a missing name, photo, or exact cash is reported before the Rider scans. A completed form is sent with `POST /api/v1/rider/delivery-proofs` using the same persistent UUID used for safe retries. The endpoint accepts JPG/JPEG/PNG/WebP up to 5 MB and stores the proof privately while recording the delivered transition in the same transaction. For COD orders whose cash is still uncollected the assignment also returns `cash_collection_required` and `cash_to_collect`; the form shows that amount, requires the Rider to type exactly that cash, and sends it as `cash_collected`, because the web API rejects the proof with 422 when the amount is missing or different. A saved proof marks the parcel delivered for every role at once: the order status and `delivered_at`, the Rider delivery task completed, the COD collection row, the shipping-earnings accrual, and buyer, seller, and station-hub notifications. Parcels then drops the parcel from the active list. The Buyer still confirms receipt separately in the web order page, then can rate purchased products. The proof does not verify GPS, recipient identity, signature, or Buyer consent. SOC5 and SOC6 are transitional API statuses and are not shown by the Rider app as proof of location in a physical SH. Actual destination-hub receipt is confirmed by that hub's web account.

The new web Logistics portal also creates Rider pickup/delivery tasks and Company Transport Driver trip manifests. `POST /api/v1/rider/tasks/{task}/exceptions` lets an assigned Rider report an issue; it pauses that task, notifies the relevant parties, and does not claim the parcel was returned. Station staff must verify custody before reassigning it. Approved Transport Drivers use separate credentials and secure token storage for `POST /api/v1/transport-drivers/login`, `GET /trips`, trip `/depart` and `/arrive`, `/earnings`, and `/logout`. The app shows the driver's assigned manifests and actions; station parcel scans are still required before the server accepts trip departure/arrival. Driver earnings are the same accrued per-hub ledger allocations, not payouts. Do not treat a planned route or a trip button as a scan or physical custody proof.

### COD cash on hand

The Earnings tab also reads `GET /api/v1/rider/cash`. It shows **Cash on hand**: the COD cash the Rider has collected from buyers and still physically holds, the number of parcels it came from, and the last 100 collections with order number, date, amount and a rider-facing status (`Still with you`, `Received by station`, or `Discrepancy`). The card says plainly that this is not the Rider's pay; it leaves the total only when the Station Hub records receipt in the web Cash Collections page. A failed cash request shows an inline retry and does not hide the accrued-earnings section. Transport Driver earnings hide this section because drivers do not collect COD.

On a delivery assignment with `cash_collection_required`, `DeliveryDetailScreen` shows a **Collect ₱X cash** card from the on-the-way-to-buyer stage onward, with the rule that the buyer pays the exact amount and that the Rider enters it in the proof form. The proof dialog still requires that exact amount, and the server rejects any other value with 422 before saving anything.

## Daily delivery window and reschedule

Every delivery attempt is due before the center's daily cutoff, 5:00 PM by default (`DELIVERY_CUTOFF` on the web app). The assignment API returns `delivery_window` with `cutoff_label`, `deadline_label`, `closed`, `scheduled_for`, `scheduled_for_label` and `reschedulable`. `DeliveryDetailScreen` shows a matching card: **Deliver before 5:00 PM** with the deadline, **Scheduled for &lt;date&gt;** when another attempt is booked, and **Delivery window closed** after the cutoff. The app reads the server's labels and flags; it does not decide the time itself.

When the cutoff passes without a delivery, the web API marks the parcel `delivery_failed` and keeps it in the Rider's list under a new **Failed** filter. The detail page then offers **Reschedule for tomorrow**; after the Rider confirms, `POST /api/v1/rider/deliveries/{order}/reschedule` books the next day. The parcel returns to the list as **For delivery** with **Scheduled for &lt;date&gt;**, and the scan button stays disabled until that day. The web API rejects `out_for_delivery` and `delivered` scans after the cutoff, and `out_for_delivery` before the scheduled day, so a hot-reloaded stale screen cannot bypass the window.

No push or background timer is involved. A closed app learns about the closed window the next time it loads the Parcels tab (opening the tab, pull to refresh, or a notification that opens the tab).

## Integration configuration

- Default production API: `https://vendo-ph.app/api/v1/rider` over HTTPS. A Linux debug build defaults to `http://127.0.0.1:8000/api/v1/rider`, so the local Laravel server must be running on port 8000. Location-load errors display the API URL to make a missing or outdated backend clear.
- For an Android emulator and a locally served backend, build with `--dart-define=VENDO_API_BASE_URL=http://10.0.2.2:8000/api/v1/rider` if port 8000 is the web server's port. An Android emulator cannot use its own `127.0.0.1` to reach the host. The debug manifest permits local HTTP; release remains HTTPS only. A physical device needs a server address reachable from its network. To point a Linux debug build at the deployed API, pass `--dart-define=VENDO_API_BASE_URL=https://vendo-ph.app/api/v1/rider`.
- Dependencies for HTTP, secure token storage, camera scanning, `google_sign_in`, and `url_launcher` are declared in `vendo_rider/pubspec.yaml` and resolved in `pubspec.lock`. Android declares package-visibility queries for `tel`, `sms`, and `smsto` in `AndroidManifest.xml`; iOS lists `tel` and `sms` under `LSApplicationQueriesSchemes` in `Info.plist`. Without these, `launchUrl` can report that no dialer or messaging app exists. The Rider Google plugin supports Android/iOS/macOS, not Linux desktop. Configure the Google Cloud OAuth clients: Android package name plus signing SHA fingerprints, iOS bundle/client ID plus reversed client URL scheme, and macOS bundle/client ID plus its callback URL scheme. Pass the server/web client with `--dart-define=GOOGLE_WEB_CLIENT_ID=...`; iOS/macOS can pass `--dart-define=GOOGLE_IOS_CLIENT_ID=...` or `--dart-define=GOOGLE_MACOS_CLIENT_ID=...`. These IDs must be allowed by the web API's `GOOGLE_ALLOWED_CLIENT_IDS`. Google sign-in cannot run on the Linux desktop client; email OTP and password-reset API flows still work there. No app tests, builds, or device walkthroughs were run by the agent per the owner's instruction.
- Android/iOS use `mobile_scanner` with QR and Code 128 explicitly enabled. On Linux, the scan screen starts the system `zbarcam --raw` webcam reader with those two formats enabled and waits for an exact tracking-number match. `zbarcam` opens its own preview window; no camera image or decoded mismatched code is uploaded. Install Fedora's `zbar` package before using this path. The owner still needs to verify both printed formats with a real device or webcam.

### Fedora Linux desktop prerequisite

The Linux implementation of `flutter_secure_storage` compiles against `libsecret-1`. On Fedora, install its development package before building the desktop app:

```bash
sudo dnf install libsecret-devel zbar
```

Then retry `flutter run -d linux` from `vendo_rider/`. This package is a machine-level build prerequisite; it is not a Laravel migration or a Flutter source change. The Fedora runtime package `libsecret` is already present on the current development machine, but `libsecret-devel` was missing on 27 September 2026. The agent could not install it because sudo required the owner's password and did not run the app.
