# Mobile feature status

**Reviewed:** 30 October 2026

| Area | Current state | Remaining work |
| --- | --- | --- |
| Rider registration | Refreshed four-step form still sends personal, Motorcycle/Van/L300/Truck vehicle, residence, and document data to the web API after six-digit email OTP or server-verified Google email proof. Google newcomers complete the regular application; matched hub review is still required. | Hub reviewer document access and no-GPS hub matching remain. Bundled PSGC data needs periodic refresh. Google sign-in requires OAuth setup and Android/iOS/macOS. |
| Rider authentication | Refreshed login calls the API; approved rider password or Google login obtains the seven-day Sanctum token and opens the five-tab Dashboard. Logout revokes the token. Forgot Password verifies email OTP, resets the password, and revokes existing rider tokens. The Profile tab opens separate Personal Information, Vehicle Details, and Change Password screens; the first two read the Rider's own record from `GET /api/v1/rider/profile` and the third updates the password through `PUT /api/v1/rider/profile/password`. Personal Information also edits the Rider's full name and birthday with `PUT /api/v1/rider/profile` and sets the account photo with `POST /api/v1/rider/profile/photo`; contact details, address, vehicle, documents, and the hub assignment remain hub-managed. | Google OAuth setup and owner verification are pending; Google is unavailable on Linux desktop. |
| API-backed rider work and dashboard | Dashboard Home reads assignment totals, first assigned parcel, and accrued earnings; Parcels is `DeliveriesScreen`, which lists assigned work and opens `DeliveryDetailScreen` for QR/Code 128 scans, private delivery proof, and active task issue reports. Delivery proof is an inline form on the detail screen (recipient name, camera or gallery photo, COD cash when required) rather than a dialog, and is validated before the scanner opens; the detail screen also shows the exact amount to collect before handover, a buyer-pin map with an Open map action, and call/SMS buttons for the recipient. A saved proof marks the parcel delivered for the Rider, Buyer, Seller, and station hub. A picked-up parcel shows an "On the way to <origin hub>" state; an out-for-delivery parcel points at the Buyer. Linux uses the system webcam reader; Android/iOS use the Flutter scanner. Approved Transport Drivers have their own mobile trip login, manifests, depart/arrival and earnings view. The dashboard Notifications tab reads Rider-scoped updates from the authenticated API; Map screen code remains but is not reachable from dashboard navigation. | Owner migration and mobile/device verification remain. Orders without a Buyer pin have no destination marker. Road routing and turn-by-turn directions are not included. Actual destination receipt remains a Logistics web confirmation. Delivery attempts close at 5:00 PM; a parcel still out for delivery is marked Delivery Failed and the Rider can reschedule the next attempt for tomorrow from the detail page. A broad offline queue remains open. |
| Dashboard Notifications and Earnings | Notifications reads Rider-scoped updates from the authenticated web API and supports read state. While the dashboard is open it polls every 25 seconds, shows an unread badge on the Notifications tab, and slides a dismissible banner over the top of the app for new items; tapping the banner opens the tab. Earnings reads the Rider or Transport Driver accrued shipping-earnings ledger from the scoped API, shows only server amounts/counts, and clearly distinguishes accrual from payout. For Riders it also loads `GET /api/v1/rider/cash` and shows **Cash on hand**: COD cash collected from buyers that the Station Hub has not received yet, with the per-parcel collections and a plain explanation that this is buyer cash, not Rider pay. | Polling is not push: a closed app receives nothing until it is opened. Older unread items do not raise a banner on first sign-in. Payout execution/reversal are not implemented. |
| Transport Driver app | `vendo_driver` Flutter app in the Vendo palette. Registration is a four-step form copied from the Rider layout that posts to `/api/v1/transport-drivers`: identity with email OTP, PSGC address, vehicle and licence with private uploads, and the Apply-to choice (Station Hub only, Province Hub only, or Both). Sign-in stores the Sanctum token, explains a pending or rejected application, and a status sheet reads the decision without a password. The app reopens a saved session through `GET /api/v1/transport-drivers/me`, so a revoked token, a suspension or an expired licence returns to sign-in, and the Profile tab shows the driver the web approved (both hubs, the linked Station Hub and the applied-to scope). Forgot Password resets the password with the web's emailed code and signs every device out. The role rules live in the web app: a station-only driver is approved by its Station Hub; province and both drivers by the Province Hub, with the Station Hub read-only. Trip screens (home, trips, manifest, dispatch, handover, legacy earnings) still use in-memory demo data. | Trip screens are not API-backed yet. No push notification for an approval decision; the app shows it on the next sign-in or status check. Password recovery needs the web to deliver the email. No scanning, container labels, incident report, trip history, notifications or salary. Device review remains. |
| Buyer registration prototype | New multi-step registration UI has personal details, an email-verification modal, ID capture, address fields, terms checkbox, review and success screen. | It does not call a Buyer API: OTP verification and success are visual only, and no Buyer account is created. Buyer app remains separate from this Rider integration. |
| Buyer home shell | Login opens `HomeScreen` with four tabs (Home, Saves, Notification, Profile). Home carries the branded header, search bar, category strip, deals banner and API product grid; Saves is the API wishlist, Profile is the API-backed account area (Personal Information with photo, Delivery Address, Change Password, My Orders with To Ship/To Receive/To Review, Saved Items, My Vouchers, My Reviews, Notifications, Help & FAQ, Rate the App, Terms and Privacy), and Notification is still a placeholder. The bottom navigation is a separate widget, `features/home/widgets/buyer_nav_bar.dart`, styled like the Rider dashboard bar: a floating, fully rounded, mostly transparent frosted bar with a shadow and one dark pill that stretches toward the tapped tab, hops and settles with an elastic bounce. It is icons only, so the bar stays short; the tab name is the button's accessibility label. The shell uses `extendBody`, so content is visible behind the bar, and Home, Saves and Profile reserve bottom clearance for it. Tab changes fire a selection haptic, tabs expose selected state to screen readers, and back returns to Home. | Notification tab is not wired to `/notifications` yet. Cart, checkout, product and seller pages are pushed routes rather than tabs. Owner device verification remains. |

Status describes code scope, not a claim of device or production testing. The owner performs acceptance testing.

Buyer registration limits phone entry to 11 digits and validates the `09XXXXXXXXX` format. Registration remains a visual prototype and does not create a Buyer account.
