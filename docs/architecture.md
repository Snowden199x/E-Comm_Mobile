# Mobile architecture

**Reviewed:** 28 September 2026

`vendo_rider/` is a Flutter application. Its registration screen uploads rider details and verification photos to `POST /api/v1/rider/register`; it loads province/city options from `GET /api/v1/rider/locations` and barangays from `GET /api/v1/rider/locations/{cityCode}/barangays`. The Laravel server verifies all three address codes and selects a unique approved, active logistics hub. The mobile app never sends a logistics-center ID.

Rider email is verified before registration by a six-digit OTP or a one-use Google registration proof. Google proves only the email; applicants still complete all profile, address, password, and document fields and wait for hub approval. After approval, the rider can use password login or exchange a Google ID token at `POST /api/v1/rider/google`. Forgot Password uses `/password/otp/send`, `/password/otp/verify`, and `/password/reset`; a successful reset revokes existing Rider API tokens. `google_sign_in` supports Android/iOS/macOS, not Linux desktop.

After hub approval, the rider signs in through `POST /api/v1/rider/login`. The bearer token, registered vehicle type, and rider/hub labels are stored with `flutter_secure_storage`. New Rider applications select Motorcycle, Van, L300, or Truck; the web API returns the saved vehicle type at login and the work screen labels the account accordingly. Motorcycle, Van, and L300 use local pickup/delivery assignments; only Truck receives linehaul assignments. The live work screen reads only `GET /api/v1/rider/assignments`, reads the label's QR or Code 128 tracking number with explicitly configured `mobile_scanner` on Android/iOS or `zbarcam` on Linux, and sends `POST /api/v1/rider/scans` with a stable client UUID for retry. Logout calls the API token-revocation endpoint. Linux debug builds default to `http://127.0.0.1:8000/api/v1/rider`; other builds default to `https://vendo-ph.app/api/v1/rider`. Any build can override the API with `--dart-define=VENDO_API_BASE_URL=...`. Android requires Internet and camera permission; iOS requires camera/photo-library usage descriptions. Linux requires the system `zbar` command and `libsecret-devel` to build.

The existing dashboard, earnings, maps, and delivery-detail screens contain prototype data and are not the live work path. The old registration email-verification modal was a prototype; the current registration flow uses real API-backed email OTP or Google verification. `vendo_buyer/` remains outside this rider change. The mobile app does not connect directly to the web database. The web app owns approval, assignment, parcel state, notifications, and the seller/buyer timeline.

The Rider app exposes the supported seller pickup, origin Main Hub arrival, out-for-delivery, and delivered scans. Legacy SOC-coded scan actions remain in the API but are not presented as physical SH arrivals by the app. The buyer confirms receipt separately before product rating. Truck linehaul assignments now include the planned route and next checkpoint as read-only data. The API does not yet support truck departure/arrival, SH arrival/sorting, or custody handoff; the separate SH scanner app owns actual SH events and route progression. Independent delivery proof, push notifications, and offline scan queues need separate backend contracts. The app must not show those stages as completed without server confirmation.

The Android debug manifest permits cleartext HTTP for a local development endpoint. The release manifest does not enable cleartext, so production uses HTTPS.
