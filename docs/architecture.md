# Mobile architecture

**Reviewed:** 12 October 2026

`vendo_rider/` is a Flutter application. Its registration screen uploads rider details and verification photos to `POST /api/v1/rider/register`; it loads province/city options from `GET /api/v1/rider/locations` and barangays from `GET /api/v1/rider/locations/{cityCode}/barangays`. The Laravel server verifies all three address codes and selects a unique approved, active logistics hub. The mobile app never sends a logistics-center ID.

Rider email is verified before registration by a six-digit OTP or a one-use Google registration proof. Google proves only the email; applicants still complete all profile, address, password, and document fields and wait for hub approval. After approval, the rider can use password login or exchange a Google ID token at `POST /api/v1/rider/google`. Forgot Password uses `/password/otp/send`, `/password/otp/verify`, and `/password/reset`; a successful reset revokes existing Rider API tokens. `google_sign_in` supports Android/iOS/macOS, not Linux desktop.

After hub approval, the rider signs in through `POST /api/v1/rider/login`. The bearer token, registered vehicle type, and rider/hub labels are stored with `flutter_secure_storage`. New Rider applications select Motorcycle, Van, L300, or Truck; the web API returns the saved vehicle type at login and the work screen labels the account accordingly. Motorcycle, Van, and L300 use local pickup/delivery assignments; only Truck receives linehaul assignments. The API-backed `RiderWorkScreen` reads `GET /api/v1/rider/assignments`, scans the label's QR or Code 128 tracking number with explicitly configured `mobile_scanner` on Android/iOS or `zbarcam` on Linux, and sends rider scans with stable client UUIDs for retry. Truck assignments return the next facility in `planned_route.scan_target`; the app submits it through `POST /api/v1/rider/facility-scans`. Successful password and Google login now open the API-backed `RiderWorkScreen`. The five-tab `DashboardScreen` remains prototype content and is not the login destination. Logout calls the API token-revocation endpoint. Linux debug builds default to `http://127.0.0.1:8000/api/v1/rider`; other builds default to `https://vendo-ph.app/api/v1/rider`. Any build can override the API with `--dart-define=VENDO_API_BASE_URL=...`. Android requires Internet and camera permission; iOS requires camera/photo-library usage descriptions. Linux requires the system `zbar` command and `libsecret-devel` to build.

The five-tab post-login dashboard shell contains prototype parcel, earnings, delivery-detail, and fixed-map content. It is no longer routed from successful login; Rider operations open the API-backed assigned-work and scan screen. Rider registration still uses real API-backed email OTP or Google verification. `vendo_buyer/` remains a separate prototype, and its redesigned registration UI does not submit to a Buyer API. The mobile app does not connect directly to the web database. The web app owns approval, assignment, parcel state, notifications, and the seller/buyer timeline.

The Rider app exposes seller pickup, origin Main Hub arrival, out-for-delivery, delivered, and assigned Truck facility scans. Truck scans share the Logistics facility workflow for origin departure, station arrival/sorting, and intermediate departure. Legacy SOC-coded actions remain for historical routes and are not presented as physical facility arrivals. Buyer receipt confirmation remains separate. Truck route stops and the next eligible scan target come from the web API. Scans are assigned operator reports; manifests and independent custody handoff remain future work. Independent delivery proof, push notifications, and offline scan queues need separate backend contracts. The app must not show those stages as completed without server confirmation.

The Android debug manifest permits cleartext HTTP for a local development endpoint. The release manifest does not enable cleartext, so production uses HTTPS.
