# Mobile architecture

**Reviewed:** 23 October 2026

`vendo_rider/` is a Flutter application. Its registration screen uploads rider details and verification photos to `POST /api/v1/rider/register`; it loads province/city options from `GET /api/v1/rider/locations` and barangays from `GET /api/v1/rider/locations/{cityCode}/barangays`. The Laravel server verifies all three address codes and selects a unique approved, active logistics hub. The mobile app never sends a logistics-center ID.

Rider email is verified before registration by a six-digit OTP or a one-use Google registration proof. Google proves only the email; applicants still complete all profile, address, password, and document fields and wait for hub approval. After approval, the rider can use password login or exchange a Google ID token at `POST /api/v1/rider/google`. Forgot Password uses `/password/otp/send`, `/password/otp/verify`, and `/password/reset`; a successful reset revokes existing Rider API tokens. `google_sign_in` supports Android/iOS/macOS, not Linux desktop.

After hub approval, the rider signs in through `POST /api/v1/rider/login`. The bearer token, registered vehicle type, and rider/hub labels are stored with `flutter_secure_storage`. New Rider applications select Motorcycle, Van, L300, or Truck; the web API returns the saved vehicle type at login and the work screen labels the account accordingly. Motorcycle, Van, and L300 use local pickup/delivery assignments; legacy Truck accounts receive linehaul assignments. Successful password and Google login open the five-tab `DashboardScreen`; Home reads `GET /api/v1/rider/assignments` for live counts and the first assigned parcel. The Parcels tab embeds `RiderWorkScreen`, which scans the label's QR or Code 128 tracking number with `mobile_scanner` on Android/iOS or `zbarcam` on Linux and sends stable client UUIDs for retry. Truck assignments return the next facility in `planned_route.scan_target`; the app submits it through `POST /api/v1/rider/facility-scans`. For new facility-routed deliveries, it captures recipient name and photo and submits `POST /api/v1/rider/delivery-proofs`. The Earnings tab reads the signed-in Rider's accrued per-hub credits from `GET /api/v1/rider/earnings`; Transport Drivers have the same earnings view from their separate token/session. These are accrued ledger amounts, not completed payouts. The Map tab reads live device location and the assigned delivery's optional Buyer pin from `GET /api/v1/rider/assignments`. It shows destination/location markers, not road routing or turn-by-turn navigation. Profile uses saved Rider details and API logout. Linux debug builds default to `http://127.0.0.1:8000/api/v1/rider`; other builds default to `https://vendo-ph.app/api/v1/rider`. Any build can override the API with `--dart-define=VENDO_API_BASE_URL=...`. Android requires Internet and camera permission; iOS requires camera/photo-library usage descriptions. Linux requires the system `zbar` command and `libsecret-devel` to build.

The five-tab Rider dashboard's Home, Parcels, and accrued Earnings data are API-backed; Map destination routes remain unavailable rather than sample data. Rider registration still uses API-backed email OTP or Google verification. `vendo_buyer/` remains a separate prototype, and its redesigned registration UI does not submit to a Buyer API. The mobile app does not connect directly to the web database. The web app owns approval, assignment, parcel state, notifications, and the seller/buyer timeline.

The Rider app exposes seller pickup, origin Main Hub arrival, out-for-delivery, delivered, assigned Truck facility scans, and task issue reports. Truck scans share the Logistics facility workflow for origin departure, station arrival/sorting, and intermediate departure. Facility-routed delivery completion captures recipient name and photo through `POST /api/v1/rider/delivery-proofs`. A separate Transport Driver login receives only its assigned manifest and can depart/arrive only after required parcel scans. Legacy SOC-coded actions remain for historical routes and are not presented as physical facility arrivals. Buyer receipt confirmation remains separate. Rider and Transport Driver accrued earnings come from completed verified route stops; the API/app do not execute payouts. Truck route stops and the next eligible scan target come from the web API. Scans are assigned operator reports. Push notifications and broad offline scan queues remain separate future work. The app must not show stages as complete without server confirmation.

The Android debug manifest permits cleartext HTTP for a local development endpoint. The release manifest does not enable cleartext, so production uses HTTPS.
